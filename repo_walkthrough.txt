 Part 1: The Big Picture — How Everything Connects

  Think of this repo as a static website factory. There is no server running in production. At build time,
  Astro reads your source files, renders every page to plain HTML/CSS, and spits out a dist/ folder. Netlify
  serves that folder. That's it.

  The request lifecycle (there is none)

  This is the most important mental model shift. Unlike Next.js, Django, or Express — there is no server
  processing requests at runtime. Every URL a visitor hits is a pre-built .html file sitting on Netlify's
  CDN. The "dynamic" parts are:

  1. Contact form — browser POSTs directly to Formspree (third-party). No backend.
  2. CMS — runs entirely in the browser at /admin/. Authenticates via Netlify Identity, then commits files to
   GitHub through Netlify's Git Gateway. Those commits trigger a rebuild.

  The build pipeline

  Developer pushes code ──┐
                          ├──> GitHub main ──> Netlify detects ──> runs `astro build` ──> deploys dist/
  CMS editor publishes ───┘

  Both developers and content editors converge on the same Git workflow. The CMS is just a friendly UI for
  making git commits.

  ┌───────────────────┬─────────────────────────────────────────────────┐
  │      Package      │                      Role                       │
  ├───────────────────┼─────────────────────────────────────────────────┤
  │ astro             │ Static site generator — the core                │
  ├───────────────────┼─────────────────────────────────────────────────┤
  │ tailwindcss       │ Utility-first CSS framework                     │
  ├───────────────────┼─────────────────────────────────────────────────┤
  │ @tailwindcss/vite │ Vite plugin to wire Tailwind into Astro's build │
  ├───────────────────┼─────────────────────────────────────────────────┤
  │ @astrojs/sitemap  │ Auto-generates sitemap XML at build time        │
  └───────────────────┴─────────────────────────────────────────────────┘

  No React, no Vue, no database driver, no API client. The simplicity is deliberate.

  How a page gets built (tracing one request)

  Let's say a visitor hits mcsc-holding.com/fr/. Here's what happened at build time to create that page:

  astro build
      │
      ├── reads src/pages/fr/index.astro
      │       │
      │       ├── sets locale = 'fr'
      │       ├── imports Layout, Navbar, Hero, ... Footer
      │       │       │
      │       │       ├── each component calls t('key', 'fr')
      │       │       │       │
      │       │       │       └── looks up key in src/i18n/fr.json
      │       │       │
      │       │       └── InsightsNews calls getLocalizedInsights('fr')
      │       │               │
      │       │               ├── reads ALL markdown in src/content/insights/
      │       │               ├── groups by slug, picks .fr variant
      │       │               └── falls back to .en if .fr is missing
      │       │
      │       └── renders to HTML string
      │
      └── writes dist/fr/index.html

  At runtime, Netlify just serves dist/fr/index.html. Zero computation.

⏺ Part 2: Astro's Component Model & Routing

  What is an .astro file?

  Every .astro file is a single-file component split into two halves by a --- fence. The top
  half is server-side TypeScript that runs only at build time. The bottom half is an HTML
  template. There is no virtual DOM, no hydration, no client-side rendering.

  ┌─────────────────────────────────┐
  │  ---                            │  ← Fence open
  │  // TypeScript (build-time)     │
  │  import X from './X.astro';     │
  │  const data = await fetch(...); │
  │  ---                            │  ← Fence close
  │                                 │
  │  <div>                          │  ← HTML template
  │    <X prop={data} />            │     (with JSX-like expressions)
  │    <p>{data.title}</p>          │
  │  </div>                         │
  └─────────────────────────────────┘

  The key insight: everything between the fences is thrown away after build. It never ships to
   the browser. This is why the bundle is tiny — visitors get pure HTML and CSS, no framework
  runtime.

  The three kinds of .astro files in this repo

  src/
  ├── pages/              ← PAGES: define URLs
  │   ├── index.astro          /
  │   ├── privacy.astro        /privacy/
  │   ├── legal.astro          /legal/
  │   ├── insights/
  │   │   ├── index.astro      /insights/
  │   │   └── [slug].astro     /insights/nil-rights-european-football/
  │   ├── fr/
  │   │   ├── index.astro      /fr/
  │   │   ├── privacy.astro    /fr/privacy/
  │   │   ├── legal.astro      /fr/legal/
  │   │   └── insights/
  │   │       ├── index.astro  /fr/insights/
  │   │       └── [slug].astro /fr/insights/nil-rights-european-football/
  │   └── it/                  (same mirror as fr/)
  │
  ├── components/         ← COMPONENTS: reusable building blocks
  │   ├── Navbar.astro
  │   ├── Hero.astro
  │   ├── ContactForm.astro
  │   └── ... (12 total)
  │
  └── layouts/            ← LAYOUTS: page shells that wrap content
      ├── Layout.astro         (base: <html>, <head>, SEO, fonts)
      └── ArticleLayout.astro  (article: hero image, prose styling)

  File-based routing: file path = URL

  Astro's rule is dead simple. Take the file path under src/pages/, strip the extension, and
  that's your URL:

  FILE PATH                              URL
  ─────────────────────────────────────  ──────────────────────
  src/pages/index.astro                  /
  src/pages/privacy.astro                /privacy/
  src/pages/insights/index.astro         /insights/
  src/pages/insights/[slug].astro        /insights/:slug/     (dynamic)
  src/pages/fr/index.astro               /fr/
  src/pages/fr/insights/[slug].astro     /fr/insights/:slug/

  There is no router config file. No routes.ts. The filesystem is the router.

  Dynamic routes: [slug].astro

  The square brackets mean "this page is generated once per item." Look at how
  src/pages/insights/[slug].astro works:

  ┌─────────────────────────────────────────────────────┐
  │  ---                                                │
  │  export async function getStaticPaths() {           │
  │    const articles = await getLocalizedInsights('en');│
  │    return articles.map(({ entry, slug }) => ({      │
  │      params: { slug },    ← URL parameter           │
  │      props: { entry },    ← data passed to template │
  │    }));                                             │
  │  }                                                  │
  │                                                     │
  │  const { entry } = Astro.props;                     │
  │  const { Content } = await render(entry);           │
  │  ---                                                │
  │                                                     │
  │  <ArticleLayout title={entry.data.title} ...>       │
  │    <Content />                                      │
  │  </ArticleLayout>                                   │
  └─────────────────────────────────────────────────────┘

  At build time, Astro calls getStaticPaths(), gets back a list like:

  [
    { params: { slug: "nil-rights-european-football" },     props: { entry: ... } },
    { params: { slug: "governance-high-net-worth-athletes"}, props: { entry: ... } },
    { params: { slug: "monaco-summit-recap" },              props: { entry: ... } },
  ]

  Then it renders the template three times, producing three HTML files:

  dist/
  └── insights/
      ├── nil-rights-european-football/index.html
      ├── governance-high-net-worth-athletes/index.html
      └── monaco-summit-recap/index.html

  Every component receives locale as a prop. That's the only coordination needed — each
  component independently calls t(key, locale) to get its translated strings.

  Where's the JavaScript?

  Almost nowhere. This site ships essentially zero JavaScript to visitors, with two
  exceptions:

  1. Navbar hamburger — a small inline <script> in Navbar.astro that toggles the mobile menu.
  ~20 lines, no framework.
  2. Netlify Identity widget — loaded in Layout.astro for CMS authentication. Only relevant to
   editors hitting /admin/.

  This is Astro's "zero JS by default" philosophy. You opt in to JavaScript, not out. If you
  ever need React or Vue interactivity, Astro supports "islands" — isolated interactive
  components — but this site hasn't needed any.

  The <slot /> pattern

  Layouts use <slot /> (borrowed from Web Components) to inject children:

  Layout.astro                          Page using it
  ─────────────                         ──────────────
  <html>                                <Layout locale="fr">
    <head>...</head>                      <Navbar locale="fr" />
    <body>                                <Hero locale="fr" />
      <slot />  ◄──── children go here    ...
    </body>                             </Layout>
  </html>

  ArticleLayout.astro nests inside Layout.astro, adding article-specific chrome (hero image,
  prose styles), then uses its own <slot /> for the rendered Markdown body.

  Layout
  └── ArticleLayout
      └── <slot />  ← rendered Markdown content goes here

⏺ Part 3: The i18n System — Three Languages, One Codebase

  Internationalization in this repo operates on three independent layers, each solving a
  different problem. Understanding which layer does what is the key to not getting confused.

  ┌──────────────────────────────────────────────────────────────────┐
  │                     THE THREE i18n LAYERS                        │
  │                                                                  │
  │  LAYER 1: URL ROUTING            "Which language page am I on?"  │
  │  ─────────────────────                                           │
  │  Astro config + filesystem       /         → English             │
  │                                  /fr/      → French              │
  │                                  /it/      → Italian             │
  │                                                                  │
  │  LAYER 2: UI TRANSLATIONS        "What does the button say?"     │
  │  ────────────────────────                                        │
  │  JSON files + t() function       t('contact.submit', 'fr')       │
  │                                  → "Envoyer"                     │
  │                                                                  │
  │  LAYER 3: CONTENT LOCALIZATION   "Which article body do I show?" │
  │  ─────────────────────────────                                   │
  │  Markdown file variants          test-title-sports.en.md         │
  │  + getLocalizedInsights()        test-title-sports.fr.md         │
  │                                  test-title-sports.it.md         │
  └──────────────────────────────────────────────────────────────────┘

  Let's trace each layer.

  ---
  Layer 1: URL Routing

  Configured in astro.config.mjs:

  i18n: {
    defaultLocale: 'en',
    locales: ['en', 'fr', 'it'],
    routing: {
      prefixDefaultLocale: false,   // ← English has NO /en/ prefix
    },
  }

  This means the URL structure is asymmetric:

  English (default)          French               Italian
  ─────────────────          ──────               ───────
  /                          /fr/                 /it/
  /insights/                 /fr/insights/        /it/insights/
  /insights/my-article/      /fr/insights/...     /it/insights/...
  /privacy/                  /fr/privacy/         /it/privacy/
  /legal/                    /fr/legal/           /it/legal/

  This is not automatic. Astro doesn't duplicate pages for you. Each locale has its own
  physical page files:

  src/pages/
  ├── index.astro                 ← English home (locale = 'en')
  ├── fr/
  │   └── index.astro             ← French home  (locale = 'fr')
  └── it/
      └── index.astro             ← Italian home (locale = 'it')

  The French and Italian pages are near-identical copies of the English ones. The only
  difference is one line:

  English:   const locale = 'en' as const;
  French:    const locale = 'fr' as const;
  Italian:   const locale = 'it' as const;

  Everything else — the imports, the component tree — is the same. The locale prop cascades
  down, and each component translates itself.

  Helper functions in src/i18n/utils.ts handle URL awareness:

  getLocaleFromUrl(url)          Parses "/fr/insights/" → 'fr'
                                 Parses "/insights/"    → 'en' (default)

  getLocalePath(path, locale)    getLocalePath('/insights/', 'fr') → '/fr/insights/'
                                 getLocalePath('/insights/', 'en') → '/insights/'

  ---
  Layer 2: UI Translations

  This is the simplest layer. Three JSON files hold key-value pairs:

  src/i18n/
  ├── en.json    { "nav.home": "Home",    "contact.submit": "Send Message",     ... }
  ├── fr.json    { "nav.home": "Accueil", "contact.submit": "Envoyer",          ... }
  └── it.json    { "nav.home": "Home",    "contact.submit": "Invia il Messaggio", ... }

  The t() function does the lookup with a double fallback:

  t(key, locale)
      │
      ├── 1. Try translations[locale][key]     ← "Do we have it in French?"
      │      found? return it
      │
      ├── 2. Try translations['en'][key]       ← "Fall back to English"
      │      found? return it
      │
      └── 3. Return the key itself             ← "contact.submit" as last resort

  t('contact.submit', 'fr')

    Step 1: fr.json["contact.submit"] → "Envoyer"  ✓  return "Envoyer"

  t('some.missing.key', 'fr')

    Step 1: fr.json["some.missing.key"] → undefined
    Step 2: en.json["some.missing.key"] → undefined
    Step 3: return "some.missing.key"    (visible in HTML — easy to spot)

  Every component uses this pattern:

  ---
  import { t, type Locale } from '../i18n/utils';
  const { locale = 'en' } = Astro.props;
  ---

  <h2>{t('group.headline', locale)}</h2>
  <p>{t('group.body', locale)}</p>

  There are ~88 translation keys. They cover navbar, hero, licenses, group description,
  expertise cards, people section, locations, insights, contact form, and footer.

  ---
  Layer 3: Content Localization (the tricky one)

  UI labels are short strings. But articles are entire Markdown documents with frontmatter.
  This layer handles which version of an article to show for a given locale.

  The file naming convention

  src/content/insights/
  ├── nil-rights-european-football.md        ← English only (no suffix)
  ├── governance-high-net-worth-athletes.md  ← English only (no suffix)
  ├── monaco-summit-recap.md                 ← English only (no suffix)
  ├── test-title-sports.en.md                ← English variant
  ├── test-title-sports.fr.md                ← French variant
  └── test-title-sports.it.md                ← Italian variant

  Two patterns coexist:
  - Single-language articles: just slug.md → treated as English
  - Multilingual articles: slug.en.md, slug.fr.md, slug.it.md

  The Astro ID gotcha

  Here's where it gets interesting. Astro's glob loader strips dots from filenames when
  creating IDs:

  FILENAME                        ASTRO ID
  ──────────────────────────      ────────────────────────────
  test-title-sports.en.md    →   "test-title-sportsen"     (dot removed!)
  test-title-sports.fr.md    →   "test-title-sportsfr"
  monaco-summit-recap.md     →   "monaco-summit-recap"     (no dot, no change)

  The getLocalizedInsights() function in src/i18n/content.ts must reverse-engineer this.
  Here's its logic:

  getLocalizedInsights(locale)
      │
      │  PHASE 1: DETECT locale variants
      │  ────────────────────────────────
      │  For each entry ID, check: does it end with "en", "fr", or "it"?
      │  AND does a sibling with a different locale suffix exist?
      │
      │    "test-title-sportsen"  ends with "en"
      │    "test-title-sportsfr"  exists?  YES → base = "test-title-sports"
      │                                         this IS a locale variant
      │
      │    "monaco-summit-recap"  ends with... nothing standard
      │                           → plain English file, no variants
      │
      │  PHASE 2: GROUP by base slug
      │  ───────────────────────────
      │
      │    "test-title-sports" → { en: entry1, fr: entry2, it: entry3 }
      │    "monaco-summit-recap" → { en: entry4 }
      │    ...
      │
      │  PHASE 3: RESOLVE per locale with fallback
      │  ──────────────────────────────────────────
      │
      │  For locale='fr':
      │
      │    "test-title-sports":
      │       fr variant exists AND has title? → USE French version
      │       (merge: FR fields override EN, empty fields fall back to EN)
      │
      │    "monaco-summit-recap":
      │       no fr variant → USE English version as fallback
      │
      │  PHASE 4: SORT by publishDate descending
      │
      └── return resolved articles

  The merge strategy is important. When a French variant exists but has an empty coverImage,
  it inherits the English one:

  EN frontmatter:                    FR frontmatter:
    title: "NIL Rights"               title: "Droits NIL"
    coverImage: "photo.jpg"           coverImage: ""          ← empty
    excerpt: "English excerpt"        excerpt: "Extrait FR"

  MERGED result for locale='fr':
    title: "Droits NIL"              ← FR wins (non-empty)
    coverImage: "photo.jpg"          ← EN fallback (FR was empty)
    excerpt: "Extrait FR"            ← FR wins (non-empty)

  Why the "garden" problem matters

  The word "garden" ends with "en". Is it a locale suffix? No. The code handles this by
  checking whether sibling locale variants exist:

  "garden" ends with "en"
    → does "gardfr" exist? NO
    → does "gardit" exist? NO
    → conclusion: "en" is part of the word, NOT a locale suffix
    → treat as plain English file with slug "garden"

  This is a heuristic, not a guarantee. It works because the CMS always creates files in
  locale sets (slug.en.md + slug.fr.md + slug.it.md together).

  ---
  How all three layers connect for a single page request

  Let's trace /fr/insights/test-title-sports/ from build to browser:

  BUILD TIME
  ──────────

  1. Astro finds src/pages/fr/insights/[slug].astro
         │
         ▼
  2. Calls getStaticPaths()
         │
         ├── getLocalizedInsights('fr') runs
         │       │
         │       ├── Reads ALL .md files from src/content/insights/
         │       ├── Groups by base slug
         │       ├── For "test-title-sports": picks FR variant, merges with EN
         │       └── Returns [{ slug: "test-title-sports", entry: mergedFR }, ...]
         │
         └── Returns [{ params: { slug: "test-title-sports" }, props: { entry } }]
                │
                ▼
  3. Renders ArticleLayout with FR entry data
         │
         ├── title = "Test Title Sports" (from FR frontmatter)
         ├── Layout wraps with <html lang="fr">
         ├── Navbar calls t('nav.home', 'fr') → "Accueil"
         └── Markdown body rendered to HTML
                │
                ▼
  4. Writes dist/fr/insights/test-title-sports/index.html

  RUNTIME
  ───────

  5. Visitor hits /fr/insights/test-title-sports/
  6. Netlify CDN serves the pre-built HTML file
  7. Done. No computation.

  ---
  The language switcher

  In Navbar.astro, the language switcher links are built with getLocalePath():

  Current page: /fr/insights/    (locale = 'fr')

  EN link: getLocalePath('/', 'en') → "/"
  FR link: getLocalePath('/', 'fr') → "/fr/"
  IT link: getLocalePath('/', 'it') → "/it/"

  Note: the switcher always links to the homepage of each locale, not the equivalent page. So
  clicking "IT" from /fr/insights/ takes you to /it/, not /it/insights/. This is a design
  choice, not a limitation.

⏺ Part 4: Content Collections & Decap CMS — From Editor to Page

  This part covers the content pipeline: how articles and team data are defined, how editors
  create content through a GUI, and how that content becomes HTML pages.

  ---
  Two content collections

  Astro's Content Collections API gives you typed, validated data from flat files. This repo
  defines two collections in src/content.config.ts:

  src/content/
  │

  The editorial workflow

  The CMS config enables publish_mode: editorial_workflow. This means content doesn't go
  straight to main. Instead:

  EDITOR ACTION              GIT RESULT                    STATUS IN CMS
  ─────────────              ──────────                    ─────────────
  "Save"                     Creates a new branch          "Draft"
                             + pull request on GitHub

  "Mark as Ready"            Updates the PR                "In Review"
                             (label change)

  "Publish"                  Merges the PR into main       "Published"
                             → triggers Netlify build
                             → live on site

  This is why you see PRs like cms/insights/test-title-sports in the git history — those are
  CMS-initiated branches.

  CMS i18n: how multilingual content is created

  The CMS config declares i18n with structure: multiple_files:

  i18n:
    structure: multiple_files      ← one file PER locale
    locales: [en, fr, it]
    default_locale: en

  When an editor creates an article called "test-title-sports", the CMS generates three files:

  src/content/insights/
  ├── test-title-sports.en.md     ← English
  ├── test-title-sports.fr.md     ← French
  └── test-title-sports.it.md     ← Italian

  Each field in the CMS config declares its i18n behavior:

  fields:
    - { name: "title",    i18n: true      }   ← translated per locale
    - { name: "category", i18n: duplicate  }   ← same value copied to all locales
    - { name: "coverImage", i18n: duplicate }  ← same value copied to all locales
    - { name: "excerpt",  i18n: true      }   ← translated per locale
    - { name: "body",     i18n: true      }   ← translated per locale

  i18n: true       → editor writes DIFFERENT content per language tab
  i18n: duplicate  → value is COPIED identically to all locale files

  So publishDate and coverImage are the same across all three files, but title, excerpt, and
  body can differ.

  Media handling

  media_folder: "public/images/uploads"    ← where files are saved in the repo
  public_folder: "/images/uploads"         ← URL path used in Markdown/frontmatter

  When an editor uploads an image through the CMS, it commits the file to
  public/images/uploads/ and references it as /images/uploads/photo.jpg in the Markdown. At
  build time, Astro copies public/ to dist/ as-is, so the URL just works.

  In practice, most images in this repo are externally hosted on Google's CDN
  (lh3.googleusercontent.com), so the upload folder is mostly for future CMS uploads.

⏺ Part 6: SEO & Structured Data — Making the Site Visible to Machines

  SEO in a static site has a huge advantage: every page is pre-rendered HTML. Search engines see
  exactly what visitors see. No JavaScript rendering required, no hydration delays, no "please wait"
   spinners. But you still need to tell machines what the content means. This repo does that across
  five mechanisms.

  ---
  The five SEO mechanisms

  ┌───────────────────────────────────────────────────────────────────┐
  │                                                                   │
  │  1. META TAGS            What shows in Google search results      │
  │  2. HREFLANG TAGS        Which language version to show whom      │
  │  3. JSON-LD              Rich snippets, knowledge panel data      │
  │  4. OPEN GRAPH / TWITTER What shows when someone shares a link    │
  │  5. SITEMAP + ROBOTS     What to crawl, what to ignore            │
  │                                                                   │
  └───────────────────────────────────────────────────────────────────┘

  All of 1-4 live in Layout.astro (the base layout every page uses). Mechanism 5 is file-based.

  ---
  1. Meta tags

  <title>{title}</title>
  <meta name="description" content={description} />

  Every page passes title and description as props to Layout.astro. Defaults exist if none are
  provided:

  Default title:       "MCSC Management | Global Sports Consulting & Management"
  Default description: "Providing clear governance and strategic advisory for
                        the next generation of sporting icons and entities."

  Article pages override these via ArticleLayout.astro:

  title:       "{Article Title} | MCSC Management"
  description: {article excerpt from frontmatter}

  ---
  2. Hreflang tags — cross-language signals

  This is the most critical SEO mechanism for a multilingual site. Hreflang tags tell Google: "this
  page exists in other languages — here's where to find them."

  Layout.astro generates these dynamically:

  CURRENT PAGE: /fr/insights/

  GENERATED TAGS:
  ┌────────────────────────────────────────────────────────────────────┐
  │ <link rel="alternate" hreflang="en"                                │
  │       href="https://mcsc-management.com/insights/" />              │
  │                                                                    │
  │ <link rel="alternate" hreflang="fr"                                │
  │       href="https://mcsc-management.com/fr/insights/" />           │
  │                                                                    │
  │ <link rel="alternate" hreflang="it"                                │
  │       href="https://mcsc-management.com/it/insights/" />           │
  │                                                                    │
  │ <link rel="alternate" hreflang="x-default"                         │
  │       href="https://mcsc-management.com/insights/" />              │
  └────────────────────────────────────────────────────────────────────┘

  The logic strips the locale prefix from the current URL, then rebuilds it for each locale:

  currentPath = Astro.url.pathname.replace(/^\/(fr|it)/, '') || '/';

  FOR EACH LOCALE:
    en  →  https://mcsc-management.com{currentPath}           (no prefix)
    fr  →  https://mcsc-management.com/fr{currentPath}
    it  →  https://mcsc-management.com/it{currentPath}

  x-default → same as English (the fallback for unmatched locales)

  What Google does with this:

  GOOGLE SEARCH              USER'S LANGUAGE     RESULT SERVED
  ──────────────             ───────────────     ─────────────
  "MCSC management"          Browser lang: fr    → /fr/
  "MCSC management"          Browser lang: it    → /it/
  "MCSC management"          Browser lang: de    → /  (x-default = English)
  "MCSC management"          Browser lang: en    → /

  ---
  3. JSON-LD structured data

  JSON-LD is invisible to visitors but parsed by search engines to build rich results (knowledge

  Organization (every page, via Layout.astro)

  ┌──────────────────────────────────────────────────────┐
  │  {                                                   │
  │    "@type": "Organization",                          │
  │    "name": "MCSC Management",                        │
  │    "foundingDate": "1993",                           │
  │    "address": [                                      │
  │      { "addressLocality": "Monaco",  "country": "MC" }│
  │      { "addressLocality": "Milan",   "country": "IT" }│
  │      { "addressLocality": "Lugano",  "country": "CH" }│
  │    ]                                                 │
  │  }                                                   │
  │                                                      │
  │  WHAT GOOGLE DOES WITH IT:                           │
  │  ┌───────────────────────────────┐                   │
  │  │ MCSC Management               │                   │
  │  │ Sports advisory firm          │                   │

                                                                                      merges PR

  How it's wired in code

  Two pieces in Layout.astro:

  Piece 1 — Load the Identity widget on every page (so it's available at /admin/):

  <script is:inline src="https://identity.netlify.com/v1/netlify-identity-widget.js"></script>

  Piece 2 — After login, redirect to the CMS:

  <script is:inline>
    if (window.netlifyIdentity) {
      window.netlifyIdentity.on("init", user => {
        if (!user) {
          window.netlifyIdentity.on("login", () => {
            document.location.href = "/admin/";
          });
        }
      });
    }
  </script>

  This handles the edge case where an editor clicks a Netlify Identity confirmation email link — it lands on
  the homepage, Identity fires, and this script bounces them to /admin/.

  Why is:inline?

  Astro normally processes <script> tags — bundling, deduplicating, adding type="module". The is:inline
  directive tells Astro: leave this script exactly as-is. No bundling, no processing. This is necessary
  because:

  - The Identity widget is an external URL that must load synchronously
  - The redirect script references window.netlifyIdentity which the external script creates

  Google Fonts

  The simplest integration. Two fonts loaded via <link> tags in Layout.astro:

  REQUEST CHAIN:

  Browser loads page
      │
      ├── <link rel="preconnect" href="https://fonts.googleapis.com" />
      │   (opens TCP connection early — saves ~100ms)
      │
      ├── <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin />
      │   (fonts served from different domain than CSS)
      │
      └── <link href="https://fonts.googleapis.com/css2?family=..." rel="stylesheet" />
              │
              ▼
      Google returns CSS with @font-face rules
              │
              ▼
      Browser downloads .woff2 files from fonts.gstatic.com
              │
              ▼
      Fonts render. Before loading: browser shows fallback system font.
      `display=swap` in the URL ensures text is visible immediately
      with a system font, then swaps to the web font when ready.

  Weights loaded:

  DM Sans:          300 (light), 400 (regular), 500 (medium), 600 (semibold)
  Playfair Display: 400 (regular), 700 (bold)

  Local development

  Saving build minutes: the Netlify CLI approach

  This is what you asked about. The key insight: you can upload a local build to Netlify without triggering
  their build pipeline.

  Setup (one time)

  npm install -g netlify-cli
  netlify login                    # opens browser for OAuth
  netlify link                     # links this directory to your Netlify site

  The workflow

  LOCAL MACHINE                                    NETLIFY
  ─────────────                                    ───────

  npm run build          Build locally
      │                  (your CPU, your time,
      │                   zero Netlify minutes)
      │
      ▼
  dist/ folder ready
      │
      │
      ├── OPTION A: Draft deploy (shareable preview, NOT production)
      │
      │   netlify deploy --dir=dist
      │       │
      │       └──────────────────────────────────► Uploads dist/
      │                                            Returns unique URL:
      │                                            https://64a3f2b1--mcsc-holding.netlify.app
      │
      │   Share that URL with anyone.
      │   It won't expire but also won't
      │   affect production.
      │
      │
      └── OPTION B: Production deploy (replaces live site)

          netlify deploy --dir=dist --prod
              │
              └──────────────────────────────────► Uploads dist/
                                                   Atomically replaces
                                                   mcsc-holding.com

  METHOD                        BUILD MINUTES USED    BUILD LOCATION
  ──────                        ──────────────────    ──────────────
  Push to main (auto-deploy)    ~1-2 minutes          Netlify servers
  PR preview deploy             ~1-2 minutes          Netlify servers
  netlify deploy --dir=dist     0 minutes             Your machine
  netlify deploy --prod         0 minutes             Your machine

  Practical scenario

  You're iterating on CSS changes and want to preview on mobile. Instead of pushing 10 commits:

  # Change something
  npm run build && netlify deploy --dir=dist

    Draft URL: https://abc123--mcsc-holding.netlify.app

  # Open on phone, check it, adjust
  npm run build && netlify deploy --dir=dist

    Draft URL: https://def456--mcsc-holding.netlify.app

  # Happy with it? Ship to production
  npm run build && netlify deploy --dir=dist --prod

    Live URL: https://mcsc-holding.com

  # Zero build minutes consumed. Push the code to git afterward.
  git add src/styles/global.css
  git commit -m "Adjust card hover shadow"
  git push

  Wait — won't that push trigger a Netlify build? Yes. To prevent that:

  Locking deploys

  In the Netlify dashboard: Deploys → Lock published deploy

  LOCKED STATE:
    ┌──────────────────────────────────────────┐
    │  Pushes to main → Netlify sees them      │
    │                 → Does NOT build         │
    │                 → Does NOT deploy        │
    │                                          │
    │  netlify deploy --prod → still works     │
    │  (manual deploys bypass the lock)        │
    └──────────────────────────────────────────┘

  This is the "budget mode": lock deploys, only use CLI deploys. Unlock when you want auto-deploys back (e.g.,
  for CMS editorial workflow, which needs auto-deploy to work).

  ---
  Stopping CMS-triggered builds

  Each time an editor publishes through Decap CMS, it merges a PR to main, which triggers a build. If editors
  publish frequently, this eats minutes. Options:

  OPTION                          TRADE-OFF
  ──────                          ─────────
  Lock deploys                    CMS publishes won't go live until
                                  you manually unlock + rebuild

  Build hooks with                Only specific events trigger builds,
    branch deploy controls        but more complex to configure

  Batch CMS publishes             Tell editors to save drafts, then
                                  you do one manual deploy per day

  TASK                              COMMAND
  ────                              ───────
  Start dev server                  npm run dev
  Build for production              npm run build
  Preview production build          npm run preview
  Draft deploy (no build minutes)   npm run build && netlify deploy --dir=dist
  Prod deploy (no build minutes)    npm run build && netlify deploy --dir=dist --prod
  Check Astro version               npx astro --version
  Add an Astro integration          npx astro add <name>
